# Case study: cleaning 50,000 rows of real-world public records

**What this is:** a self-initiated sample project, built to show exactly what my
data-cleanup service delivers. It is **not client work** — there is no client,
and the dataset is public data published by the City of Chicago. Every number
below comes from the actual script run on the actual file; both are in this
folder, so you can re-run it and check.

**How it was produced (disclosed up front):** my process is
automation-assisted — I use AI coding tools (Claude Code) to write and run the
cleaning pipeline, and I personally review the rules, the output, and every
number before anything ships. That combination is the point of the service:
script-speed on 50,000 rows, with a human accountable for every decision.

---

## The dataset

- **Source:** City of Chicago Data Portal — *Food Inspections*
  (dataset id `4ijn-s7e5`), also cataloged on data.gov.
- **Slice used:** the 50,000 oldest rows (inspections 2010-01-04 to
  2012-09-13), 15 columns, pulled 2026-08-29 via the portal's public API:

  ```
  https://data.cityofchicago.org/resource/4ijn-s7e5.csv
    ?$select=inspection_id,dba_name,aka_name,license_,facility_type,risk,
             address,city,state,zip,inspection_date,inspection_type,results,
             latitude,longitude
    &$order=inspection_date ASC,inspection_id ASC
    &$limit=50000
  ```

- **Repository note:** the full `raw_food_inspections.csv` (11 MB) and
  `cleaned.csv` (9 MB) are kept out of git to keep this repo light — a 500-row
  sample (`raw_sample_500.csv`) is committed instead. To reproduce the full run,
  download the dataset with the API query above (save as
  `raw_food_inspections.csv`) and run `python3 clean.py`; the printed report
  should match `validation_report.md` exactly.
- **Why this one:** it is real operational data — business names, addresses,
  license numbers, categories, dates — entered by many hands over years.
  It has the same failure modes as a typical CRM or sales export, and none of
  them were staged: every problem below shipped in the city's own export.

## What was actually wrong (with real examples from the file)

- **Duplicates:** 113 inspections were entered twice — identical in all 14
  content columns, only the system row-ID differs. Notably, **2 of the 113
  were invisible until after standardization**: stray whitespace made the
  copies look different to a naive dedupe. Order of operations matters.
- **Whitespace noise:** 48,951 cells — including 46,526 addresses with
  stray whitespace, most of them trailing spaces like `"608 W BARRY AVE "` —
  which silently breaks joins, lookups, and pivot tables.
- **One city, nine spellings:** `CHICAGO`, `Chicago`, `chicago`, `CHicago`,
  `CCHICAGO`, `CHCHICAGO`, `CHCICAGO`, `CHICAGOCHICAGO`, `CHICAGOI` — plus
  text in the city column that is not a city at all (`INACTIVE`, and
  `CHARLES A HAYES` — a name that leaked in from another field).
- **Category sprawl:** 290 spellings of `facility_type` (`TAVERN` vs
  `Tavern` vs `tavern`, `Convenience Store` vs `CONVENIENCE STORE` vs
  `convenience store`, the misspelling `RESTUARANT AND BAR`);
  98 spellings of `inspection_type` (`Out of Business` vs `OUT OF BUSINESS`,
  `No Entry` vs `NO ENTRY` vs `no entry`).
- **Invalid codes:** 3 rows with risk category `"All"` (not a defined value);
  235 rows using `"0"` as the license number.
- **Missing data:** 2,260 rows missing `facility_type`, 947 missing
  `aka_name`, 187 missing coordinates, and more — reported per column in the
  validation report, **never invented**.
- **Dates:** uniform but bloated — every date carried a meaningless
  `T00:00:00.000` midnight timestamp; standardized to `YYYY-MM-DD`.
  (This particular file parsed cleanly with zero corrupted rows — the
  pipeline checks for them anyway, and quarantines any it finds.)

## Methodology — and the rules I won't break

The pipeline (`clean.py`, ~420 commented lines) runs ten steps: structural
integrity scan → whitespace normalization → date standardization → city
standardization → state/ZIP validation → risk-code validation → category
canonicalization → placeholder removal → coordinate sanity check → duplicate
removal. Three principles govern every step:

1. **No destructive guessing.** Unambiguous fixes (a documented misspelling
   of Chicago) are corrected by an explicit, reviewable mapping table.
   Ambiguous values (`INACTIVE` as a city; a possible duplicate where the
   two rows differ) are **flagged in a `qa_flags` column, not silently
   deleted or "fixed."** Business names keep their original casing — `NoMi`
   is a name, not a typo.
2. **Everything is counted.** Every rewrite, clear, and drop lands in the
   validation report with a number you can check against the files.
3. **Deletions are auditable.** The 113 removed duplicates aren't gone —
   they're in `duplicates_removed.csv` so you can verify each one.

Judgment calls are documented in place: the 571 near-duplicates (same
license + date + inspection type, but some field differs) are flagged for
review rather than dropped, because resolving them needs business context I
don't have — and on a real engagement, that's a question I ask you rather
than a decision I bury in a script.

## Honest limitations of this sample

- `facility_type` still has 263 labels after cleanup. Collapsing the
  remaining compound labels (`Grocery/Restaurant` vs `Restaurant/Grocery`)
  changes what the data *means*, so it requires the owner's vocabulary — on
  client work that's a 15-minute review list, not a silent merge.
- The source file's dates were uniformly formatted; when a client file mixes
  `03/04/2021`, `4-Mar-21`, and Excel serial numbers, the same
  parse-validate-flag approach applies, but that case isn't demonstrated here.
- This is public civic data. Client files are handled under stricter rules:
  process disclosure before work starts, data minimized to what the job
  needs, files deleted after the revision window.

```
pip install pandas
```

`duplicates_removed.csv`, and `validation_report.md` in place. Total runtime
on this 50,000-row file: under 30 seconds on a laptop-class machine.
